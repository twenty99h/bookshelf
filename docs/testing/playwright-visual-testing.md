# Playwright и визуальные E2E Bookshelf

Статус: согласованная стратегия проверки будущей UX-переработки. Конкретные зависимости, команды и CI jobs определяются реализационной спецификацией.

## Цель

Playwright должен одновременно давать агенту быстрые воспроизводимые скриншоты и защищать основные пользовательские сценарии. Скриншот является главным утверждением для геометрии, темы, видимости и композиции; тесты не дублируют его отдельными проверками каждого текста, цвета или control.

Скриншот не подтверждает постоянное сохранение, IPC, focus и доступность. Эти свойства покрываются небольшим отдельным набором невизуальных инвариантов.

## Контуры проверки

### Browser E2E

Основной Playwright suite запускает production-like frontend в Chromium с browser test adapter, реализующим тот же интерфейс предметных команд, что и Tauri adapter. Test adapter:

- получает детерминированный начальный снимок от fixture builder;
- обслуживает локальный тестовый PDF;
- возвращает устойчивые идентификаторы и время;
- записывает выполненные команды для проверки невидимых side effects;
- имитирует ошибки и загрузку по явному сценарию;
- никогда не входит в production bundle.

Реальный Codex во всех E2E заменяется контролируемыми ответами, включая success, отсутствие входа, crash, отмену и ручной fallback.

### Нативные smoke-тесты

Отдельный небольшой suite позднее проверяет собранное Tauri-приложение:

1. импорт PDF через системную границу;
2. выдачу локального URL и открытие reader;
3. сохранение и восстановление позиции после перезапуска.

Он не повторяет визуальную матрицу и не обращается к реальному Codex. Конкретный Windows driver выбирается отдельной реализационной спецификацией.

### Component и domain tests

Vitest/Testing Library остаются для локального поведения сложных контролов и page model, Rust tests — для доменных инвариантов, persistence, архивов и IPC contracts. После появления E2E удаляются только дублирующие frontend-тесты, а не проверки поведения, которое скриншот не наблюдает.

## Page Object Model

Page Object инкапсулирует доступные локаторы и пользовательские действия, но не строит данные и не содержит assertions. Fixtures создают состояние до открытия страницы; spec владеет ожиданиями и скриншотами.

Предлагаемая структура:

```text
e2e/
  fixtures/
    library-fixtures.ts
    bookshelf-test.pdf
  pages/
    app.page.ts
    dashboard.page.ts
    library.page.ts
    reader.page.ts
    drafts.page.ts
    knowledge.page.ts
    practice.page.ts
    settings.page.ts
  specs/
    visual/
    behavior/
    accessibility/
  snapshots/
```

Тестовый PDF живёт рядом с E2E-фикстурами, потому что production UI его не использует. Он содержит 8–12 собственных страниц, текстовый слой, оглавление, схему, изображение, повторяемые поисковые фразы и абзац через границу страниц. Авторские права третьих лиц не используются.

Пример разделения ответственности:

```ts
const reader = new ReaderPage(page);
await reader.openBook("book-active");
await reader.selectFixturePassage("source-fragment-2");
await reader.saveDraft("Проверить ограничение");

await expect(page).toHaveScreenshot("reader-saved-draft.png");
expect(await testAdapter.commands()).toContainEqual(
  expect.objectContaining({ kind: "captureDraft", bookId: "book-active" }),
);
```

## Визуальная матрица

Начальный набор ограничен примерно двенадцатью устойчивыми экранами:

| Baseline | Состояние |
| --- | --- |
| `dashboard-active` | Активная книга, незавершённая работа и недельные вехи |
| `library-list` | Плотная библиотека с разными статусами |
| `book-overview` | Страница активной книги |
| `reader-clean` | Непрерывный reader без сайдбара |
| `reader-note` | Выделение и форма черновика |
| `reader-outline` | Оглавление и цифровое поле книги |
| `drafts-review` | Последовательный разбор черновика |
| `idea-detail` | Master-detail знаний |
| `practice-active` | Восстановление и эксперименты |
| `book-completion` | Пошаговое завершение изучения |
| `settings-backup` | Резервные копии и состояние архива |
| `first-run` | Пустая библиотека и один основной CTA |

Ошибки, hover/focus, Codex feedback и варианты PDF проверяются региональными скриншотами ключевой области, а не полными копиями каждого экрана.

Основные baselines снимаются при `1920×1080`. Функциональный suite дополнительно проходит при `1280×720`, где master-detail может стать drawer. Мобильные viewport не добавляются.

## Невидимые инварианты

Минимальный поведенческий набор:

1. позиция, масштаб и reader layout восстанавливаются после перезагрузки;
2. выделение действительно сохраняется как черновик;
3. черновик превращается в идею с сохранённым источником;
4. смена активной книги приостанавливает предыдущую;
5. нативный импорт открывает реальный PDF через Tauri.

Новые инварианты добавляются только вместе с поведением, которое не видно на скриншоте.

## Клавиатура и доступность

Один keyboard-only сценарий проходит reader без мыши: открыть сайдбар, найти текст, сохранить черновик через `Ctrl+Enter`, закрыть контекст через `Esc` и проверить возврат focus. Ключевые страницы проходят автоматическую accessibility-проверку; она не заменяет ручную проверку порядка focus и announcements.

## Детерминизм

- IBM Plex поставляется локально, CI не загружает шрифты из сети.
- Время, даты, идентификаторы и locale фиксированы.
- PDF.js дожидается явного состояния готовности, а не произвольного timeout.
- Анимации и caret отключаются на момент снимка.
- Browser, OS image, device scale factor и viewport закреплены.
- Данные теста сбрасываются перед каждым spec.
- Скриншот Chromium является визуальным контрактом; WebView2 проверяется нативным smoke, но не отдельным полным набором baseline.

## Обновление baseline

Эталоны обновляются только явной локальной командой. CI никогда не принимает новое изображение автоматически и при несовпадении публикует expected, actual и diff. Изменение baseline должно сопровождаться объяснением пользовательского изменения в PR.

Допустимый порог пиксельного различия выбирается после первых стабильных прогонов и не используется для маскировки систематических расхождений. Сначала устраняется источник недетерминизма, затем обсуждается tolerance.
